Backup system · design and operations

pqbox: post-quantum encrypted backups for a one-person homelab

Three tiers, two destinations on three machines, one key pair that the automation can use to write and never to read. Built and verified on a single NixOS host with 64 PostgreSQL databases.

1Starting point

There was no working backup. Two things existed and both were misleading:

  • ZFS auto-snapshots (10 min, hourly, daily, weekly, monthly) on the same pool. Useful for rollback after a mistake, useless against disk loss.
  • A single nightly pg_dump of one database, written to /root/backup on the same pool. One database out of sixty-four.

An earlier restic setup had been built, then lost with the rest of its config. Four snapshots survived on the VPS, but the repository password was gone with the deleted secret file, which made them unreadable. That failure shaped the design: a backup system whose key can disappear with a directory is not a backup system.

2Goals

  1. Write-only for the machine. The agent and the host may create archives, and must not be able to open them. Encryption keyed to a public key, private key held only by the human, sealed with a passphrase he types once and never shares.
  2. Quantum-resistant by construction. No RSA, no bare ECC in the data path. A passive attacker who archives ciphertext today must gain nothing when a large quantum computer exists.
  3. Cheap enough to leave running. A daily cycle that finishes in minutes, keeps CPU out of the way of interactive work, and does not fill a 46 GB VPS.
  4. Honest about scope. Say what is covered, what is not, and what cannot be recovered.

3Encryption

Each archive is an envelope: a fresh random content key per file, wrapped to a long-term hybrid KEM public key.

LayerPrimitiveWhy this one
Key establishmentML-KEM-768 (FIPS 203) + X25519, mixed with HKDF-SHA256Shor breaks X25519, so it cannot carry the secret alone; ML-KEM carries it against quantum attackers. Mixing both means an attacker must break both.
DataAES-256-GCM, 1 MiB chunks, counter nonces, per-chunk AADGrover only halves the margin, leaving 128 bits; chunking keeps memory flat and makes truncation detectable.
Private key at restPBKDF2-HMAC-SHA256, 1,000,000 iterations, AES-256-GCM wrapThe key file alone is inert. The passphrase is the only thing that opens it.

What this design buys

  • Hosting providers, a stolen VPS, or an attacker with unlimited storage see blobs and nothing else. No asymmetric secret exists on any server, so there is no key to steal from the remote side.
  • Harvest-now-decrypt-later has no target in the data path: the only long-term public key is a KEM key, and the session secret is ephemeral on both sides.
  • Losing the passphrase loses the archives, by design. There is no recovery path, no escrow, no reset.
Honest limits. No cipher is proven unbreakable. ML-KEM rests on the assumed hardness of Module-LWE; NIST standardized it in 2024 as the best available option. The practical weak link is not the math, it is passphrase strength: a million PBKDF2 iterations costs an offline attacker about a second per guess, which is irrelevant against six diceware words and fatal against a ten-character human password.

4Three tiers, because not all data deserves the same treatment

Measured on the real dump: the archive was 58% one abandoned application's scraped HTML, 27% agent state, 10% the chat server, and 6% everything that actually matters day to day. Compressing all of it at maximum effort would have paid for nothing.

Compression level is assigned by tier, not globally: the core tier is small enough that 15 minutes of CPU to gain 40% is free at night, while the volume tier is dominated by incompressible attachments (99.7% ratio, 345 MB) where extra effort is pointless.

5How the snapshots accumulate

The temptation is to chase compression. The measurement says otherwise. Two dumps of the live databases taken thirty minutes apart contained 2.39 million lines, of which 5,730 were new: 0.2%. The busiest database changed 674 lines out of 1.86 million. A daily dump is 95 to 99% identical to yesterday's.

Three ways to exploit that, and why we picked what we picked:

OptionGainCostDecision

Retention is enforced on every destination after each successful copy, so disk usage is bounded by policy rather than by luck.

6Transport

Early versions shelled out to ssh and scp. That is fragile by nature: it depends on a binary in PATH, on exit codes surfaced through pipes, and on remote command quoting. The transfer layer is now a library, paramiko, driven from Python:

  • reads ~/.ssh/config, including ProxyJump chaining, so a destination behind a bastion needs no extra glue;
  • three attempts with backoff, keepalive, and explicit timeouts;
  • atomic uploads: write .part-<pid>, then rename;
  • verification after upload by running sha256sum -c on the remote side, and treating a mismatch as a hard failure on the primary destination;
  • the mirror destination is best effort: a laptop that is asleep at 03:30 must not fail the backup or page anyone.

The crypto and the orchestration live in one Python file: cryptography for the primitives, tarfile for packaging, zstd for compression, paramiko for transport. No shell pipeline, no temp files left behind, and one code path for the timer and for a human running it by hand.

7What was actually verified

  • Round-trip at edge sizes: 0, 1, 15, 1,000, chunk−1, exactly one chunk, chunk+1, and three chunks plus seven bytes.
  • Adversarial cases: one flipped bit, a truncated file, and a wrong private key are all rejected with a chunk-level authentication error.
  • Interoperability: an archive written by the previous Go implementation decrypts with the Python one and vice versa, so archives produced during the transition remain readable and the key pair did not need to change.
  • Remote paths: upload, remote checksum verification and cleanup exercised against both destinations, including the one reached through a jump host.
  • Restore, not just compression: a database section was replayed into a throwaway PostgreSQL cluster built with initdb, with the 87 roles restored first. Row counts matched the live database exactly: 4 applications, 5 clients, 543 messages, 1 user.
  • Both ends of every archive: sha256sum -c on the host and on the VPS, four archives each.

8Operating it

pqbox backup core|volume|dead|all     # build, encrypt, ship, verify, prune
pqbox decrypt --key <sealed key> --in archive.pqbox --out -
pqbox check  rack:/path              # replay remote checksums
pqbox test-ssh rack:/path            # upload, verify, delete a probe file
pqbox selftest                       # crypto + tamper + interop

Restoring a single database: decrypt the archive, decompress it, extract the section for that database, create an empty cluster, replay the roles, then psql -f. Restoring everything is the same dump in one pass.

If the passphrase is lost, the archives are lost. That is the whole point of the design and it has no workaround. The public key stays valid, so a new passphrase can be set on the same key without re-encrypting anything, but only while the old one is still known.

9Known gaps

  • Chat attachments are incompressible and make up 40% of the encrypted volume. They belong in a deduplicating repository or on object storage, not in a daily envelope.
  • The volume tier has a single destination. The mirror machine only has about 6 GB free, so it receives the core tier only.
  • No third-party copy yet. Both destinations belong to the same person, on two machines and two networks. A cheap object store would close that gap.
  • Some state is out of reach of the backup user: cloud storage files, the password vault's attachments, and the bridges' SQLite stores live under directories that require root. They need a system-level extension, not this tool.
  • The disk itself raised a flag during this work: the pool reported three data errors and one scratch file became unreadable. The affected file was disposable, and a fresh dump of the same database read back cleanly, but a single-disk pool cannot repair a bad block. Scrubbing is overdue.
